# SmartThings Generic IR Remote

An in-progress SmartThings Edge driver for TS1201 (Moes/Zosung) IR blasters. Each logical remote is intended to be an Edge child device. AC children have separate button-based, learned-state, and protocol-based profiles.

## Status

The driver includes exact learned-state control, LG/LG2 encoders, and eight additional experimental protocol variants from IRremoteESP8266. AC children expose power, AC mode, one target-temperature slider, fan speed, and supported swing directions. Native SmartThings AC modes label `dry` as **제습** in Korean. Protocol waveforms and complete Zigbee chunk transfers have local reference tests; AC compatibility still requires a physical check. Other named remote buttons are not implemented.

See [the driver design](docs/driver-design.md) for the intended behavior and acceptance checks, [the implementation plan](docs/implementation-plan.md) for the remaining work, and [protocol sources](docs/protocol-sources.md) for encoder references.

## Create remotes and learn signals in the app

After installing this version, reopen the blaster page. Choose **Remote type**,
enter **Remote name**, and tap **Create remote**. The creation status confirms
when the child is added. Existing devices request the updated GUI profiles on
startup, keeping their saved codes and preferences.

On a TV, fan or generic remote, choose **Power on** or **Power off**, tap **Learn
selected signal**, then press the original remote button. **Cancel**, **Test**,
**Delete**, saved-signal status and learning/timeout/error status appear on that
page. Test completion means the blaster transfer finished.

For AC capture, enable **Edit capture state without sending**. Set power, mode,
temperature, fan and swing using the usual controls; these edit an isolated draft
without IR transmission. Set the original remote to the same state, tap **Learn**,
and send its command. Use **Test** to transmit the saved state. Disable setup mode
to restore normal controls; captures remain saved. Legacy token-based Settings
requests continue to work. See the [GUI guide](capabilities/README.md).

## How to run

Run commands from the repository root.

### Run the local Lua checks

Install a Lua 5.3 interpreter, then run the standalone checks individually:

```sh
lua tests/ac_state.lua
lua tests/ac_registry.lua
lua tests/ac_protocols.lua
lua tests/ac_learned_state.lua
lua tests/children.lua
lua tests/edge_lifecycle.lua
lua tests/edge_child_control.lua
lua tests/ir_controller.lua
lua tests/edge_zigbee.lua
lua tests/ir_learned_actions.lua
lua tests/zosung.lua
lua tests/zosung_wire.lua
```

These scripts exercise state, child controls, Zosung transport and 338 waveform vectors generated by the upstream C++ library. For native SmartThings SDK serialization and capability-schema checks, extract the [official Lua libraries](https://github.com/SmartThingsCommunity/SmartThingsEdgeDrivers/releases), set `SMARTTHINGS_LUA_LIBS` to the directory containing `st/`, and run:

```sh
lua tests/edge_zigbee_sdk.lua
lua tests/edge_ac_controls_sdk.lua
lua tests/gui_sdk.lua
```

The SDK tests serialize complete on/off payload transfers for all 11 protocol choices and check the AC mode, single temperature, swing, persisted state and profile migration paths. They do not confirm physical AC reception.

### Package and install on a development hub

You need a SmartThings account, the [SmartThings CLI](https://github.com/SmartThingsCommunity/smartthings-cli#installation), a compatible SmartThings hub, and a driver channel that the hub has joined. Sign in through the CLI when prompted.

1. List your hubs and copy the development hub ID:

   ```sh
   smartthings devices --type=HUB
   ```

2. If you do not already have a driver channel, create one and follow the prompts:

   ```sh
   smartthings edge:channels:create
   ```

3. Enroll the hub in that channel, using the IDs from the previous steps:

   ```sh
   smartthings edge:channels:enroll <hub-id> --channel <channel-id>
   ```

4. Build and upload this driver package, then install it to the enrolled hub:

   ```sh
   smartthings edge:drivers:package . --install --channel <channel-id> --hub <hub-id>
   ```

   The CLI may prompt for values if flags are omitted. Re-run the package command after code changes to publish and install an updated version.

5. In the SmartThings app, add the supported TS1201 device using **Add device → Scan nearby**.

The parent receives Zosung `0xED00` messages and runs one transfer at a time. For a TV, fan, or generic remote child, open its Settings and set **Learn or cancel a power action** to a new value such as `on-001|power_on` or `off-001|power_off`; point the original remote at the blaster during capture. Use a new token for every request. Set a new `<token>|cancel` value to cancel learning. After capture, the child's switch `on` and `off` commands send only the matching saved code. Its switch state records a completed blaster transfer; it does not confirm that the TV or fan responded. Pairing, transport, and AC protocol behavior still need validation on a development hub. See the [implementation plan](docs/implementation-plan.md) before treating any feature as complete. For the full driver workflow, see the official [Edge driver packaging and deployment guide](https://developer.smartthings.com/docs/devices/hub-connected/edge-architecture) and [driver channel guide](https://developer.smartthings.com/docs/devices/hub-connected/driver-channels).

For an AC child, **AC infrared protocol** defaults to **Learn states**. Set the original remote to a complete state, aim it at the blaster, then set **Learn complete AC state** to a fresh request such as `learn-01|on|cool|24|auto|off|off`. The fields are token, power, mode (`cool`, `heat`, `dry`, `fan`, `auto`), integer Celsius temperature, fan (`auto`, `low`, `medium`, `high`), vertical swing, and horizontal swing. Capture each state you plan to use; the driver sends an exact saved match and refuses an unlearned state. `token|cancel` cancels a capture. The SmartThings controls update desired/last-commanded state after a send starts; they do not report physical AC feedback. Set **AC temperature unit** to match the SmartThings setpoint display.

The same Settings page offers these generated protocol choices. **Learning is not required** for these choices. Select the remote variant rather than assuming every AC from a brand uses the same protocol.

| Setting | Temperature | Swing control | Example upstream remote/model candidates |
| --- | --- | --- | --- |
| LG 28-bit / LG2 28-bit | 16–30 °C | Off only | GE6711AR2853M / AKB74395308; see source notes |
| LG2 AKB74955603 | 16–30 °C | Vertical | AKB74955603, AMNW09GSJA0 |
| Toshiba 72-bit A / B | 17–30 °C | Vertical | A: WH-TA04NE, WC-L03SE, WH-TA01JE; B: WA-TH03A, WA-TH04A |
| Mitsubishi Electric 144-bit | 16–31 °C | Vertical and horizontal | KM14A, SG153, RH151, SG15D; MS-GK24VA, MSZ-GV2519 |
| Gree YAW1F / YBOFB / YX1FSF | 16–30 °C | Vertical and horizontal | YAW1F; YBOFB/YBOFB2; YX1FSF/YX1F2F |
| Kelvinator 128-bit | 16–30 °C | Vertical and horizontal | YALIF, KSV26/35/53/62/70/80 series; Gree YAPOF3/YAP0F8/YAP2F |
| Electra AUX 104-bit | 16–32 °C | Vertical and horizontal | YKR-M/003E, YKR-T/011, YKR-H/102E, YKR-P/002E; Electrolux YKR-H/531E |

All generated choices remain experimental. Gree auto mode fixes the setpoint at 25 °C; dry mode fixes the fan to low. Kelvinator auto/dry modes fix the setpoint at 25 °C. Selecting those modes applies their required defaults; explicit incompatible settings are rejected. Mitsubishi swing off parks the vertical vanes at the top and horizontal vanes at the center. Extra functions such as turbo, timers, display toggles and fixed vane positions are not exposed.

The swing selector offers only directions supported by the selected protocol. Learned-state users must capture the exact on/off swing state they intend to select (`on` for an enabled direction). Generic LG/LG2 choices keep swing off because the auxiliary commands differ by remote. The explicit AKB74955603 choice sends absolute vertical swing on/off commands. The supplied LG **6711A90006C** remote remains unmapped; a brand-level match does not establish compatibility.

Both AC profiles now use **one temperature control for heating and cooling**, `airConditionerMode` (`제습`, `송풍`, etc.), and `fanOscillationMode`. Existing AC children request the updated profile when this driver starts, preserving saved IR codes and preferences. After installing, reopen the device page; existing Routines that referenced the old thermostat capabilities may need their actions reselected. Bixby phrase recognition must be checked on the user's account/device.

### Physical smoke test: learn and send a TV power code

This first hardware check assumes a TS1201-compatible Zigbee IR blaster, a SmartThings hub that supports Edge drivers, a TV, and the TV's original IR remote. Keep the remote and blaster close together for learning, then aim the blaster's IR emitter at the TV. The current fingerprint matches Zigbee profile `0x0104` devices that report server clusters `0xED00` and `0xE004`; a different hardware revision may not match.

1. Install and authenticate the SmartThings CLI. Check the CLI with `smartthings --version`, then list hubs with `smartthings devices --type=HUB`.
2. Create a driver channel if you do not already have one by running `smartthings edge:channels:create`. Enroll your development hub in that channel and package/install this checkout using the commands above. Keep the hub ID and channel ID for later updates.
3. In a second PowerShell window, start live logs for the hub (replace the address with the hub's LAN IP):

   ```powershell
   smartthings edge:drivers:logcat --hub-address=192.168.1.20
   ```

   Select this driver if the CLI asks. Leave logcat running while pairing and learning.
4. Put the blaster into Zigbee pairing mode using the reset/pairing procedure for its exact model. In the SmartThings app, choose **Add device → Scan nearby**. A successful match should appear as **IR Blaster (development)**. If it does not, confirm the model and its reported Zigbee clusters before continuing.
5. Open the blaster's Settings in the SmartThings app. Under **Add remote request**, save a fresh request such as `test-tv|remote-tv|Test TV`. The child remote should appear as a separate device.
6. Open the new child's Settings. Under **Learn or cancel a power action**, enter `learn-on-01|power_on`, save, then press the TV remote's power button while pointing it at the blaster. A successful capture logs `Learned IR action saved: power_on`; repeat with a new request, `learn-off-01|power_off`, and press the power button again. A timeout or malformed-message warning means the capture did not complete.
7. Return to the child remote and send **On**, then **Off**. Confirm that the TV responds and check logcat for the outgoing transfer and its completion. The SmartThings switch state only reports that the blaster transfer completed; verify the TV itself to confirm IR reception.

If pairing succeeds but learning or sending fails, save the logcat output and note the blaster's exact model/revision, hub model, and which step failed. This helps distinguish a fingerprint mismatch from a receive/transmit or protocol issue.

### TV buttons and learning layout

TV remotes expose navigation, digits, volume/channel, input, playback, colored
keys and other common controls. Each button must be learned separately. Learning
controls follow normal remote controls; AC learning controls disappear when a
generated protocol is selected, and return when **Learn states** is selected.

Before packaging this update, run `./capabilities/register-tv-ui.ps1` to register
the TV control capabilities and update the existing learning definition/presentation.
See [registration and button details](capabilities/README.md#tv-controls-and-updated-layout).

TV navigation now uses the standard `keypadInput` native remote capability
(arrows/OK, navigation and number pad), with learned codes mapped to its `sendKey`
command. Extra TV buttons and the bottom learning card remain available.

Child types **AC protocol** and **AC protocol with learning** now have separate
profiles. Protocol-only children contain no IR learning capability. Existing
protocol children select the appropriate profile from their encoder preference.
Run `./capabilities/register-tv-ui.ps1` before packaging to update the parent
creation choices and presentations; saved IR signals are preserved.

TV detail pages now omit all separate button rows below the native keypad.
To learn a button, choose it in **Signal to learn**, then press **Learn selected
signal** and use the original remote. Profile-defined choices expose all TV
signals even if an older device status listed only on/off. Extra signals remain
available through the learning card's Test action. Non-AC power switches now
start with a usable assumed state and retain the last successfully sent state.
